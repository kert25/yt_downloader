# Workflow (для ассистента)

Этот файл — описание работы над проектом. Ты должен прочитать его
в начале каждой сессии, чтобы понимать, как действовать.

---

## 1. Ветки

- **main** — только релизные версии, помеченные тегом.
- **develop** — основная ветка, в которую вливаются все изменения.
- Коммиты напрямую в main **запрещены**.

Каждая задача выполняется в отдельной ветке, которая потом вливается
в develop. Имя ветки: `feature/<что-делаем>` или `fix/<что-чиним>`.

После завершения задачи ветка удаляется (и локально, и на GitHub).

## 2. Правила работы

- В начале сессии — перечитать этот файл.
- Перед тем как что-то делать — `git checkout develop && git pull`.
- Новую ветку создавать от develop.
- Один PR / merge = одна логическая задача. Не мешать фичи и фиксы в одной ветке.
- После merge ветку удалять.
- Deploy и push только после проверки, что код не сломан.

## 3. Коммиты

Формат: `<тип>: <описание на русском, до 70 символов>`

Типы:
- `Add` — новая функциональность
- `Fix` — исправление бага
- `Change` — изменение логики без новой фичи
- `Remove` — удаление кода/файлов
- `Docs` — документация
- `Style` — форматирование, стиль кода

Описание без точки в конце.

## 4. Релиз

Когда develop накопил достаточно изменений для релиза:

```bash
git checkout main
git merge develop --no-ff
git tag -a v<версия> -m "v<версия> — <кратко что нового>"
git push origin main --tags
git checkout develop
```

Перед релизом обновить CHANGELOG.md (в develop) — добавить
запись о новой версии с секциями Added / Changed / Fixed / Removed.

## 5. Версионирование

SemVer: `v<MAJOR>.<MINOR>.<PATCH>`
- MAJOR — ломающие изменения
- MINOR — новые фичи
- PATCH — баг-фиксы и мелочи

Пока проект на ранней стадии — `0.x.y`.

## 6. Что проверять перед пушем

- Код запускается без ошибок (python3 app.py)
- Фронтенд не рассыпался
- Чейнджлог обновлён, если это релиз
- В коммит не попали мусорные файлы
